# Нормализация брокерских данных

`scripts/normalize_broker.py` — первый слой: преобразование сохранённых структурированных **REST JSON** ответов в наблюдаемые значения и их происхождение. Это офлайн-программа без сети. Она не собирает ответы, не проверяет подлинность источника и не создаёт готовые входы для денежных/позиционных валидаторов.

Профиль `tinvest-rest-v1` основан на официальных схемах, просмотренных 8 ноября 2026 года. Актуальная схема инструментов MCP в облачном чате пока не проверена. Ответы MCP, в том числе объекты `{currency, value}`, не следует переименовывать в этот профиль; для них нужен отдельный проверенный адаптер.

## Контракт захвата

Верхний объект:

```json
{
  "profile": "tinvest-rest-v1",
  "account_id": "synthetic-account",
  "captures": [
    {
      "capture_id": "synthetic-positions",
      "method": "GetPositions",
      "requested_at": "2026-11-08T00:00:00Z",
      "received_at": "2026-11-08T00:00:01Z",
      "request": {"accountId": "synthetic-account"},
      "response": {
        "accountId": "synthetic-account",
        "limitsLoadingInProgress": false,
        "money": [{"currency": "rub", "units": "1000", "nano": 0}],
        "blocked": [],
        "securities": [],
        "futures": [],
        "options": []
      }
    }
  ]
}
```

Это искусственная иллюстрация, а не текущий снимок. Не меняй её время ради прохождения проверки. Сохраняй исходные время начала запроса и время получения ответа при реальном сборе. Возраст измеряется от начала запроса: не более 60 секунд для позиций/метаданных и 30 секунд для лимитов. Получение старого файла сейчас не делает данные свежими. Эти метки времени предоставляются сборщиком, а не подтверждаются программой у брокера.

Допустимы только три метки метода:

| Метод | Захваченный запрос | Используемый ответ |
|---|---|---|
| `GetPositions` | `accountId` | `accountId`, `limitsLoadingInProgress`, явные массивы `money`, `blocked`, `securities`, `futures`, `options` |
| `GetInstrumentBy` | `idType: "INSTRUMENT_ID_TYPE_UID"`, `id` | `instrument`: `uid`, `positionUid`, `instrumentType`, `lot`, `currency`, булевы `buyAvailableFlag`, `sellAvailableFlag`, `apiTradeAvailableFlag` |
| `GetMaxLots` | `accountId`, `instrumentId` именно UID, явная положительная `price: {units, nano}` | `currency`, `buyLimits: {buyMaxLots, buyMoneyAmount}`, `sellLimits: {sellMaxLots}` |

Требуется ровно один `GetPositions`; для каждой позиции/лимита — один соответствующий `GetInstrumentBy`. Запросы лимитов необязательны; отсутствие запроса означает отсутствие наблюдения, а не нулевой лимит. Для одной пары UID/цена допускается один ответ лимитов. Разные цены сохраняются отдельно, их лимиты не складываются.

Профиль намеренно строгий: строки `int64`, целый `int32` для лотности, `nano` как целое в диапазоне ±999999999, согласованные знаки `units/nano`, явные массивы и булевы поля. Никаких `float` в денежных преобразованиях. При опущенном обязательном поле, snake_case вместо camelCase или неподдерживаемом методе — `BLOCK`; недостающие значения не материализуются как нули или `false`. Неизвестные дополнительные поля не интерпретируются; глубина вложенности всего захвата ограничена 64 уровнями до хеширования. Повторные JSON-ключи и нечисловые константы `NaN`/`Infinity` при чтении файла отклоняются. Перед подключением другого сериализатора нужен отдельный профиль/тесты его фактической схемы.

В `securities[]` нужны `instrumentUid`, `positionUid`, `instrumentType`, строки `balance`, `blocked` и булев `exchangeBlocked`. Поддерживаются типы `share`, `bond`, `etf` (последний отображается как `fund`). Лотность берётся из метаданных, а не угадывается по стоимости. Отрицательные балансы, непустые фьючерсы/опционы и незавершённая загрузка лимитов отклоняются консервативным профилем. Эти отказы не означают, что сам аналитический навык не может описать такие инструменты.

## Арифметика и границы достоверности

| Наблюдение | Преобразование | Чего из него не следует |
|---|---|---|
| `securities.balance` | Уже незаблокированное количество бумаг в штуках | Завершённость расчётов или собственность |
| `securities.blocked` | Заблокированное заявками количество отдельно | Что это единственная блокировка инструмента |
| Отчётное общее количество | `balance + blocked` | Что получены `settled_own_units` |
| Целые незаблокированные лоты | `balance // lot`, остаток `balance % lot` | Доступность продажи при `exchangeBlocked: true` или запрете торговли |
| `money` и денежный `blocked` | Два отдельных набора сумм по валютам | Универсальная формула `money - blocked` или подтверждённый бюджет BUY |
| `sellLimits.sellMaxLots` | Лимит по собственной позиции в лотах | Подтверждение отсутствия займа/прочих обязательств во всём счёте |
| `buyLimits.buyMoneyAmount` | Наблюдаемая сумма для конкретного инструмента/цены | Универсальный доступный остаток для всех предложений |

Положительный `sellLimits` должен помещаться в наблюдаемое незаблокированное количество целых лотов. Противоречие снимков даёт отказ, а не выбор более удобного значения. Лимиты с `margin` не используются. Биржевая блокировка сохраняется отдельным признаком; число из `balance` в таком случае нельзя считать доступным для продажи.

Для облигаций цена запроса `GetMaxLots` должна быть в валюте расчётов. Конвертация котировки в пунктах здесь не выполняется: сохранённое число — наблюдение запроса, а не доказательство корректной денежной оценки. Публичный тип `etf` также не доказывает отсутствие плеча фонда.

## Выход и использование

```bash
python3 skills/trader-tinvest/scripts/normalize_broker.py --help
python3 skills/trader-tinvest/scripts/normalize_broker.py .local/broker-captures.json
```

- `NORMALIZED_OBSERVATIONS`, код 0: формат преобразован, `ready_for_validators: false`.
- `BLOCK`, код 2: вход неполон, устарел, противоречив или вне профиля; частичные наблюдения не возвращаются.

Успешный результат содержит `observations`, `provenance` и `missing_checks`. Для каждого захвата сохраняются идентификатор, исходные метки времени и SHA-256 канонических запроса/ответа. Хеш помогает сопоставлять расчёт с сохранёнными данными; он не доказывает, что ответ получен от брокера или не был подделан вместе с хешем.

Программа не выпускает `snapshot`, `orders`, `verified`, `no_existing_debt`, `settled_own_units` или `leveraged:false`. Выход напрямую не подходит `cash_guard.py`, `sell_guard.py` и `daily_loss.py`: при такой подаче проверки должны отказать. Код 0 здесь означает только успешное преобразование формата.

Для следующего слоя ещё нужны проверенный сбор из доступного read-only подключения, отдельный адаптер фактической схемы MCP, сверка собственности/расчётов/обязательств, текущая доступность на счёте, полная стоимость предложения и неизменная дневная база с внешними потоками. Не заполняй эти пробелы ручной заменой флагов на `true`. Реальные захваты и результаты держи вне Git, например в `.local/`; заголовки авторизации и токены в них не включай.

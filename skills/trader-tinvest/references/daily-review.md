# Ежедневный обзор и расчётный план

Используй эту процедуру для ежедневного анализа с переносом позиций, если пользователь согласовал такой режим. Цель — искать положительный результат после издержек; прибыльность стратегии ещё не установлена. Публикуемый файл параметров — пример. Предпочтения берутся из явных указаний пользователя или его непубликуемого локального профиля; настройки не запускают расписание и не создают торгового исполнителя.

## Данные и результат

1. Проверь счёт и фактически доступные методы чтения. Получи портфель, остатки и блокировки, активные заявки и операции за нужный период. Не учитывай деньги других счетов, кредитные лимиты и ожидаемые продажи как доступный бюджет. Фактическую включённость маржинального режима нельзя выводить только из наличия денежных средств или статуса read-only токена. Неизвестный статус режима не мешает аналитическому обзору и сам по себе не доказывает заимствование; денежное предложение требует независимого подтверждения собственных доступных средств и полной стоимости. При отсутствии этих подтверждений предложение блокируется.
2. Установи базовую оценку капитала на начало дня в Europe/Moscow и сверенные внешние денежные потоки. Не подменяй базу текущим балансом после убытка и не сбрасывай её повторным запуском. При отсутствии проверяемой базы дневной контроль возвращает `INSUFFICIENT_DATA`, новые предложения блокируются. Для межвалютных потоков нужны проверенные курсы; при неизвестной оценке не заявляй точную прибыль.
3. Рассчитывай дневной результат как текущая оценка минус базовая оценка минус чистый внешний поток. Используемый знаменатель — базовая оценка плюс этот поток. Пополнения не являются прибылью, выводы не являются убытком. При достижении согласованного дневного порога прекрати формировать новые предложения. В примере порог равен 50%; не присваивай его новому пользователю автоматически. Это не стоп-заявка, не автоматическая ликвидация и не гарантия ограничения потерь.
4. Рассмотри доступный каталог инструментов. Для денежных предложений проверь полную оплату и ограниченные денежные обязательства. Фьючерсы с ГО, короткие позиции, заёмное финансирование, фонды с плечом и неизвестные обязательства не проходят текущий cash-only контроль. Поддерживаемые покупки — акции, облигации, фонды без плеча и спот-валюта с подтверждёнными условиями. Другие инструменты можно исследовать; не заявляй их поддержку валидатором.
5. Для кандидатов проверь торговый режим, лот, шаг цены, валюту расчётов, доступность на счёте, ликвидность, спред, новости и даты корпоративных событий. Отчётность и прогнозы должны иметь источник и дату. При облигациях различай проценты номинала, денежную цену и НКД; при фьючерсах пункты и рубли не взаимозаменяемы.
6. Описывай торговую гипотезу до оценки результата: сигнал входа, горизонт, условие пересмотра/выхода, размер и отсутствие сигнала. Пока стратегия не выбрана и не проверена, результат — исследование и список недостающих проверок, а не персональная команда купить. Оценка стратегии на истории должна исключать подсматривание будущих данных, включать отдельный проверочный период и издержки обеих сторон сделки. Записывай число сделок, чистый результат, просадку и сравнение с выбранным ориентиром. Не называй стратегию прибыльной по красивому примеру или результату до комиссий.
7. Для расчёта покупки используй лимитную цену и актуальные данные брокера. В `GetMaxLots` собственные средства представлены `buy_limits` / `buyLimits`, собственная позиция — `sell_limits` / `sellLimits`. Поля с `margin` не подходят. Подтверждай полную стоимость через `GetOrderPrice`, включая комиссии и НКД; предварительная оценка не гарантирует будущую стоимость. Сохраняй связь оценки с точным счётом, инструментом, стороной, числом лотов, ценой и временем. Складывай стоимость всех предложений в одной валюте; не используй один и тот же остаток несколько раз.
8. Подготовь нормализованные входы для отдельных офлайн-проверок. Их булевы флаги означают утверждения нормализатора о проверенных данных; выставлять их `true` по предположению нельзя. `cash_guard.py` проверяет бюджет BUY/LIMIT; SELL в нём блокируется. `sell_guard.py` проверяет только количество собственных свободных бумаг для SELL/LIMIT. Используй единый снимок с подтверждённой семантикой «собственное рассчитанное количество включает блокировку»; исключи займы и ожидаемые поступления. Совместные продажи UID должны помещаться в один свободный остаток и минимум подтверждённых `sellLimits.sellMaxLots`. Комиссии и выручку продаж этот скрипт не проверяет; не добавляй выручку в бюджет покупок. Для дневного порога используй `daily_loss.py`. Для полного контура ещё нужны нормализатор, денежная оценка продаж, выбор и оценка стратегии. Код исполнения реальных сделок отсутствует.

Для сохранённых REST-захватов доступен первый слой [нормализации](broker-normalization.md). Его наблюдения не являются входами для валидаторов: собственность, завершённость расчётов, обязательства и прочие подтверждения остаются отдельными проверками. `GetPositions.securities.balance` уже исключает блокировку заявками; отчётный итог — `balance + blocked`. Не распространяй эту формулу по аналогии на денежные поля и не подменяй ею сверку собственных рассчитанных остатков.

Отчёт: время и счёт; капитал и доступные собственные деньги по валютам; дневной результат с потоками и базой; гипотезы и издержки; причины отбраковки; статусы отдельных проверок; недостающие данные. Допустим результат «подходящих предложений нет». Не стремись потратить остаток только ради полного использования бюджета. Сохраняй источник и время расчётного снимка без токена.
